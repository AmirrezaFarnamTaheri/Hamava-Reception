# Operations, privacy and financial workflow review

## Result and scope

The implemented operations layer provides tenant-scoped staff controls, durable outreach, appointment response, capacity-based waitlist offers, deposit policy and merchant binding, refund/dispute records, clinic disruption handling and a production UAT attestation gate. The broad owned suite passed **151 tests** in **85.50 seconds** using the project Python environment. After the final waitlist terms extension, its five new cases and the existing operations/review regressions passed **34 tests** in **20.81 seconds**. The isolated review suite had also passed **16 tests**, and the owned source/test/script lint checks passed. These counts overlap; they are not added together. The exact commands and limits are recorded in `validation/operations-acceptance.json`.

These are local software results. The tests use fictional clinics/patients, disposable databases, synthetic WAV tones and mocked financial/provider boundaries. They establish no real SMS delivery, money movement, carrier readiness, medical/legal approval, consented training corpus, trained-model improvement, paid customer outcome or production operating capacity. Root-level PostgreSQL, deployment, browser and media validation have separate evidence files. A successful local test is not substituted for those gates.

The application API contracts, including exact request shapes, are in `api-contract.md`. The separate assessment in `validation/operations-requirement-evidence.json` proposes statuses for the original requirement IDs; it does not silently modify the main register. `blueprint-revision.md` preserves the complete source scope, and `launch-playbook.md` contains the work that needs real operators, counterparties and observations.

## Review findings and corrections

| Area | Defect or risk addressed | Current behavior and evidence |
|---|---|---|
| Settlement replay | A replay could overwrite financial state after refund processing. | Verified replay preserves terminal refund state. `test_replayed_settlement_after_refund_preserves_terminal_ledger`. |
| Refund evidence | Completed refund reference could change, or one transfer reference could complete two records. | Conflicting completed evidence and reference reuse are rejected. `test_completed_refund_replay_rejects_changed_evidence`, `test_one_provider_refund_reference_cannot_complete_two_ledgers`. |
| Concurrent refunds | Separate partial requests could reserve more than the actual refundable principal. | Tenant serialization and a conditional reservation update bound total requests; same-key concurrency reserves once. Concurrent completion converges without losing partial refunds. |
| Uncertain refunds | Unknown transfer outcomes could be treated as refused/failed and release funds prematurely. | Reconciliation remains reserved; evidence is required for a failed or completed outcome. Refusal/failure releases once. No refund transfer API is invented. |
| Financial history | A dispute could encourage rewriting original settlement facts. | A recorded loss appends one negative principal adjustment; duplicate transitions do not duplicate it. Refund limits subtract known principal adjustments. |
| Free-text financial notes | A staff-entered refund reason might include patient details in an ordinary ledger column. | New reasons are encrypted in scoped audit details; the ledger retains a categorical marker. Authorized retrieval and exact replay still work. Existing plaintext rows remain a migration/retention obligation. |
| Payment authority | Global merchant environment values could ambiguously determine the receiving/verifying clinic. | Actual deposits require explicit tenant-to-merchant mapping and published policy. Each intent pins merchant identity hash, alias, sandbox, currency, amount, terms and expiry before external link creation. Callback verification cannot silently switch identities. |
| Disclosure before deposit | Generic confirmation did not bind accepted deposit/cancellation/refund terms. | Actual deposit booking requires the current version and explicit acceptance. Caller readback includes the published terms and changed terms require a fresh confirmation. |
| Database transaction across provider I/O | A read transaction could remain open during external payment verification. | The lookup transaction is committed before awaiting the gateway; settlement then reacquires current tenant/payment/calendar locks. The regression observes no open transaction inside provider verification. |
| Expired waitlist outreach | An offer text could be sent after its hold expired. | Current offer status, expiry, consent and capacity are rechecked before dispatch; stale offers are suppressed and expiration/rejection is audited. |
| Privacy token survival | An accepted-offer capability could outlive a subject erasure request. | Erasure revokes offer capabilities without silently canceling retained active appointments. |
| Orphan capacity | Erasure or a lost waitlist claim could leave capacity held unnecessarily. | Active call/offer holds release immediately; lost candidate claims release their newly acquired hold. |
| Invalid local times | Waitlist windows could accept seconds or offset-bearing pseudo-local values. | The input accepts canonical local `HH:MM` minute times and rejects noncanonical values. |
| Stale reminders | A deferred reminder could be transmitted after appointment start or a policy/revision change. | Dispatch checks current start, status, revision, opt-in, offset and suppression. Missed offsets produce one latest-due reminder, not a burst. |
| Opt-out versus erasure | Deleting a record was an inappropriate substitute for purpose-specific withdrawal. | Separate authenticated revocation creates purpose tombstones, revokes grants, suppresses unsent outreach and releases eligible waitlist holds while retaining the appointment. |
| Channel preference bypass | Purpose-level permission could override an explicit SMS denial. | SMS channel denial takes precedence at enrollment, scheduling and dispatch; broad suppression remains stronger. |
| Case ownership | Parallel staff could claim or resolve someone else's case. | Claims are serialized/versioned, reassignment validates eligible active membership, and the legacy resolution route enforces the same ownership policy. |
| Correction atomicity | A failed destination move could partially update name/contact or destroy original capacity. | Corrections share the booking transaction and preserve original details/calendar on conflict; encrypted history links prior/current subject identities for privacy requests. |
| Clinic closure truth | Delays/closures could be mistaken for automatic patient rescheduling. | Blocking intervals preserve existing appointment facts, create explicit impact reviews and send minimal notices. Staff separately records keep/cancel/move decisions. |
| Staff-note erasure | Linked task notes were omitted from subject export/deletion scope. | Export/correction/deletion includes linked notes and encrypted correction history; free-text values are redacted while necessary state/ownership/categorical audit survives. |
| Aggregate definitions | Active cases and call minutes could be undercounted or inflated. | All active task states count independently of list caps; STT processing seconds never count as billable call time; unknown attendance remains unknown. |
| Integration status | Demo mode mislabeled working local media as disabled and checked an obsolete token. | Media configuration is `configured_unverified`; actual simulated sends/payments use `demo_disabled`. AudioSocket reads `MEDIA_API_TOKEN`, and LiveKit requires its approval flag and credentials. |

The two final isolated-review failures encountered during verification were corrected before the clean result: a directly used channel-permission model was registered only through another test's imports, and the new synthetic speech-configuration fixture omitted the required approved-host allowlist. The application now imports its model dependency explicitly; the fixture supplies the same allowlist that a real configuration must satisfy. No security check was relaxed.

## Transaction and state guarantees

Calendar-affecting operations acquire tenant authority before booking/capacity records. A current signed slot token still undergoes commit-time resource checks. Corrections, disruption impact changes and ordinary booking use the same calendar service. They do not maintain a second schedule. Public response capabilities authorize one response to one appointment revision; they are neither staff tokens nor proof of actual attendance.

Message state distinguishes queued, in-flight, submitted, delivered, failed, unknown and simulated outcomes. A process crash after an uncertain submission does not justify automatic resend. Existing submitted/delivered/unknown histories survive privacy cleanup as operational facts with sensitive content removed; eligible unsent messages are suppressed. A revocation response explicitly distinguishes messages already in flight, which the application cannot truthfully recall.

Waitlist auto-offer is opt-in. A release event alone does not prove capacity: the worker checks the authoritative current calendar and obtains an actual temporary hold before producing an offer. Another booking wins if it has already taken the interval. The worker bounds each run, contact frequency and lifetime attempts. Staff-triggered offers also require an actual available hold, but are an explicit staff action and do not require an automatic release event.

Refund state describes a recorded business process, not a transfer made by this code. Owner/admin can record an unexecuted refusal, an uncertain reconciliation, evidenced failure or evidenced completion. Transfer references must be unique and consistent. The original settled payment remains an immutable fact even if later adjustments or refund review change the net financial position.

## Supported limits and remaining software scope

- Service duration, buffers and named single-capacity resource bundles are supported. Arbitrary recurring appointment series, multi-instance scheduling sagas and automatic session-series reconciliation are not implemented. Each existing booking is an individual transaction with its own outcome.
- Staff correction permits name/contact and a valid new slot, including a service change with current duration/resources and explicit price approval. A changed deposit or pending-payment move requires a separate financial review/rebooking workflow; the application does not guess how to transfer money between bookings.
- Actual deposit-service waitlist acceptance now reads current safe terms through scoped staff or capability-protected public views, requires the current version and explicit acceptance, and snapshots them in the pending-payment booking. A changed policy requires refreshed readback and a new confirmation. The delivered interface uses the staff acceptance workflow; there is no advertised standalone public waitlist page or automatic bank transfer.
- Outbound voice reminders are disabled. A real approved carrier capability, quiet-hour/budget semantics and actual call-result verification must exist before dialing is implemented or advertised.
- Generic clinician-approved followup is administrative. It does not generate patient-specific medical aftercare, diagnose symptoms or certify that a named staff member has the clinical qualifications claimed in a real deployment.
- The evaluator reports supplied retry/task/handoff/outcome data only where its schema supports those metrics. It does not infer real ASR quality, actual response-time subspans or clinical safety from fictional transcripts.
- Dataset curation requires supplied provenance, permission and review evidence. It checks exact hashes, selected metadata, PCM layout, redaction spans, duration bounds and grouped splits. It does not perform automatic diarization, VAD/noise estimation, teacher-model adjudication, acoustic near-duplicate detection or universal personal-data recognition.
- Per-purpose export/audio/backup retention, complete processor legal terms, arbitrary text redaction and real data subject identification need deployment-specific operating procedures and additional supported workflows. Existing local expiry/tombstone controls must not be represented as universal privacy compliance.

## Production publication and external launch gates

Production activation requires an unexpired named UAT attestation bound to the exact clinic, target mode, policy/catalog and latest payment-policy publication. All five booking/cancel/conflict/provider-failure/handoff checks require individual evidence references. Pausing is always possible. Editing live catalog/financial policy requires pausing first. The application can verify that the authorized reviewer supplied the attestation; it cannot certify the truth of an external evidence reference.

A real launch still needs the authorized clinic operator, local legal/clinical review where applicable, processor/data-region decisions, provisioned carrier/number rights, actual SMS/payment provider credentials and contracts, staffed human fallback, target-device/network tests, approved public wording and an observed baseline. Financial merchant registry flags and UAT checkboxes are not substitutes for those facts.

Research launch additionally requires a real representative consented corpus, reviewable labels, valid code/weights/data/voice licenses, compute and a completed reproducible experiment. The delivered optional trainer is runnable after those gates but has not trained a model in this work. Its synthetic fixtures are non-speech tones. Pilot/economics reports are examples over fictional inputs; no clinic received messages, no transfer was sent, and no customer outcome was inferred.

## Operational acceptance before exposing real traffic

Follow `launch-playbook.md` and `deployment-runbook.md` to assign actual owners and evidence references. At minimum, confirm that the current tenant's terms, mode and catalog match the attested fingerprint; old pending merchant aliases remain available; queued/in-flight message definitions are understood; privacy requests can be fulfilled by authorized staff; financial review has real execution/reconciliation ownership; restore/key recovery was rehearsed; and the human fallback answers within the clinic's tested operating arrangement.

Stop automated intake for a false confirmed booking, cross-tenant exposure, fabricated settlement, unconsented recording or failed recovery that threatens calendar truth. Preserve minimal IDs and evidence, use staffed fallback, correct affected business records with authorization, and require a new scoped review before reactivation. A local test pass does not override an observed real-world failure.
