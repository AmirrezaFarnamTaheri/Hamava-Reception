# برنامه‌های ویندوز و اندروید و مهندسی انتشار

[English](clients-and-releases.md) · [مستندات](README.fa.md)

برنامهٔ React در `frontend/` رابط مشترک پذیرش را فراهم می‌کند. `apps/desktop/` با Electron آن را برای ویندوز و `apps/mobile/` با Capacitor برای اندروید بسته‌بندی می‌کند. هر دو برنامه برای نوبت، مجوز، گفت‌وگو و نتیجهٔ پرداخت به سرور مرکز وصل می‌شوند. این راهنما قابلیت‌های میزبان و روش بررسی انتشار آن را توضیح می‌دهد.

## برنامهٔ بومی چه چیزی اضافه می‌کند؟

در اجرای اول، برنامه نشانی سرور مرکز را می‌خواهد. پیش از درخواست گذرواژه، **بدون اعتبارنامه** سازگاری را با `/api/v1/client-info` می‌سنجد و فقط بعد از آن اجازهٔ ورود می‌دهد. اندروید به سرور HTTPS نیاز دارد. دسکتاپ از پل preload جداشدهٔ Electron و حفاظت نشست مبتنی بر سیستم‌عامل در صورت دسترس استفاده می‌کند؛ اندروید مخزن مبتنی بر Keystore و سیاست محدود شبکه/پشتیبان دارد.

برنامه می‌تواند در قطع موقت اتصال، نشست معتبر را حفظ کند، اما نباید ادعای نوبت‌دهی آفلاین یا بازسازی ورود باطل‌شده از مخزن قدیمی داشته باشد. خروج صریح باید در صورت دسترسی، نشست را روی سرور باطل و حتی اگر سرور در آن لحظه قطع بود، بازگشت خودکار نشست محلی را مسدود کند.

رابط مشترک راست‌به‌چپ برای کار روزانهٔ دسکتاپ و ناوبری «امروز / وظایف / تماس‌ها / بیشتر» در موبایل استفاده می‌شود. مجوز از عضویت جاری سرور می‌آید؛ تغییر مرکز باید محدودهٔ داده را تازه کند، نه فقط عنوان صفحه را عوض کند.

## ساخت رابط وب مشترک

با **Node.js 24** از ریشهٔ مخزن:

~~~sh
npm --prefix frontend ci
npm --prefix frontend run typecheck
npm --prefix frontend run build
node scripts/check-versions.mjs
~~~

فایل‌های وب در `frontend/dist/` ساخته می‌شوند. پیش از بسته‌بندی هر میزبان، آن‌ها را بسازید. هر پروژه فایل قفل وابستگی خودش را دارد؛ `node_modules` را بین پوشه‌ها کپی نکنید و نسخه‌های npm را بی‌دلیل تغییر ندهید.

## ساخت نسخهٔ دسکتاپ

روی میزبان مناسب ساخت ویندوز:

~~~sh
npm --prefix apps/desktop ci
npm --prefix apps/desktop test
npm --prefix apps/desktop run prepare:web
npm --prefix apps/desktop run test:launch
npm --prefix apps/desktop run build:win
~~~

سازنده می‌تواند نصب‌کنندهٔ NSIS و فایل اجرایی قابل‌حمل ویندوز بسازد. آزمون پل Electron رفتارهای امنیتی برنامه را می‌سنجد و آزمون اجرا میزبان واقعی را بررسی می‌کند. موفقیت کامپایل روی CI جای نصب، ارتقا و حذف در نسخه‌های واقعی ویندوز را نمی‌گیرد.

بستهٔ Linux AppImage/tar.gz نیز هدف جداگانهٔ محلی در پروژهٔ دسکتاپ دارد، اما بخشی از همان گردش‌کار انتشار ویندوز نیست.

## ساخت نسخهٔ اندروید

Java **21**، ‏Android SDK و ابزارهای ساخت لازم را نصب کنید. سپس:

~~~sh
npm --prefix apps/mobile ci
npm --prefix apps/mobile run sync
npm --prefix apps/mobile run test
npm --prefix apps/mobile run build:debug
~~~

میزبان Capacitor فایل‌های وب ساخته‌شده را مصرف می‌کند. از Gradle wrapper موجود در `apps/mobile/android/` استفاده کنید، نه نسخهٔ دلخواه نصب‌شده روی سیستم. شناسهٔ برنامهٔ debug با release متفاوت است؛ APK آزمایشی با برنامهٔ عملیاتی یا گواهی انتشار یکی نیست. گردش‌کار انتشار APK و AAB نسخهٔ release را نیز می‌سازد.

## CI، امضا و انتشار

| گردش‌کار | وظیفه |
| --- | --- |
| `.github/workflows/verify.yml` | آزمون سرور، PostgreSQL، مرورگر، پل دسکتاپ و کانتینر |
| `.github/workflows/release-apps.yml` | پس از تأیید، ساخت بسته‌های ویندوز و اندروید و جمع‌آوری هش و فهرست فایل‌ها |

گردش‌کار انتشار پرچم‌های صریح امضا دارد. انتشار ویندوز به گواهی مجاز و رمز آن و اندروید به keystore و شناسه‌های کلید بهره‌بردار نیاز دارد. وقتی امضا خواسته شده، گردش‌کار نتیجهٔ امضا را بررسی می‌کند و صرف وجود فایل را کافی نمی‌داند. اجرای امضاشده و دارای برچسب نسخه می‌تواند [یادداشت انتشار](release-notes.fa.md) را در **پیش‌نویس** GitHub Release قرار دهد؛ عمومی‌کردن انتشار یا ثبت در فروشگاه تصمیم جداگانهٔ مالک است.

نسخه میان بستهٔ ریشه، وب، برنامه‌های بومی، مشخصات Python و تصویر Compose یکسان است. `node scripts/check-versions.mjs` این تطابق و سازگاری نسخهٔ یادداشت‌های انگلیسی و فارسی را می‌سنجد.

## اولین اجرای برنامه، گام‌به‌گام

اگر برنامهٔ ویندوز یا اندروید سرور مورداعتماد ذخیره‌شده نداشته باشد، صفحهٔ اتصال مرکز را نشان می‌دهد. کاربر نشانی اصلی سرور را وارد می‌کند. برنامه بدون توکن کارمند، `/api/v1/client-info` را فراخوانی و پیش از نمایش ورود، نام محصول و سازگاری API را بررسی می‌کند.

بعد از ورود، نشست به مرکز انتخاب‌شده و عضویت فعلی کاربر در سرور وابسته است. قطع ارتباط اجازهٔ ساخت نوبت محلی نمی‌دهد. رابط می‌تواند اطلاعات لازم برای نمایش وضعیت قطع و تلاش دوباره را حفظ کند، اما نوبت و وظایف مرجع روی سرور می‌مانند.

| وضعیت | نمایش مناسب | چه قاعده‌ای حفظ شود؟ |
| --- | --- | --- |
| سرور ناشناخته یا ناسازگار | توضیح خطا و امکان اصلاح نشانی | اعتبارنامه به مبدأ تأییدنشده فرستاده نشود |
| قطع موقت شبکه | وضعیت اتصال و گزینهٔ تلاش دوباره | نوبت محلی تازه قطعی نمایش داده نشود |
| خروج کارمند در حالت آفلاین | وضعیت خارج‌شده | اعتبارنامهٔ قدیمی دستگاه نشست را پنهانی برنگرداند |
| تغییر عضویت مرکز در سرور | تأیید مجدد دسترسی یا ورود | محدودهٔ قدیمی مجوز درخواست تازه ندهد |
| ارتقای برنامهٔ نصب‌شده | بازگشت به کار مجاز پس از بررسی سازگاری | نسخهٔ برنامه با قرارداد سرور هماهنگ باشد |

در اندروید HTTPS و نگهداری نشست با Keystore بخشی از قواعد پلتفرم هستند. Electron از پل preload محدود و در صورت دسترس از مخزن محافظت‌شدهٔ سیستم‌عامل استفاده می‌کند. این تصمیم‌ها را در میزبان بومی نگه دارید و اعتبارنامهٔ حساس را داخل بستهٔ وب کپی نکنید.

## بستهٔ قابل‌انتشار به چه بررسی نیاز دارد؟

موفقیت `npm run build:win` یا `npm run build:release` ساخت بسته را نشان می‌دهد، نه پذیرش توزیع. مسئول انتشار باید نام و نسخهٔ فایل، هش SHA-256، هویت امضا، مسیر نصب، ارتقا از نسخهٔ قبلی، خروج هنگام قطع شبکه و حذف یا نصب مجدد را بررسی کند. در اندروید، رفتن به پس‌زمینه و بازگشت و درخواست مجوز میکروفون را هم در حالت صوتی آزمایش کنید.

هر اجرا به فایل واقعی ساخته‌شده وصل باشد: پلتفرم، نسخهٔ سیستم‌عامل، نام و هش فایل، نتیجهٔ امضا، دستگاه، بازبین و خطاهای مشاهده‌شده. با تغییر نسخهٔ میزبان بومی یا وابستگی، همین فهرست پذیرش را دوباره اجرا کنید.

اگر راز امضا وجود ندارد، فایل آزمایشیِ بدون امضا را با تغییر نام به انتشار عمومی تبدیل نکنید. گردش‌کار می‌تواند پیش‌نویس بسته‌ها را آماده کند، اما ناشر دربارهٔ توزیع بستهٔ امضاشده تصمیم می‌گیرد.

## آزمون لازم پیش از تحویل نصب‌کننده به کاربران

| آزمون | ویندوز | اندروید |
| --- | --- | --- |
| هویت امضا و هش بسته | Authenticode، نصب‌کننده و فایل قابل‌حمل | هویت امضای APK/AAB و نسخه |
| اجرای اول | نشانی HTTPS مرکز، بررسی سازگاری، ورود | HTTPS، سیاست شبکهٔ اندروید و ورود |
| نشست و خروج | مخزن امن، خروج در قطع اتصال، اجرای دوباره | Keystore، محدودیت پشتیبان و اجرای دوباره |
| کار روزانه | صفحه‌کلید، پنجره‌ها، تماس/وظیفه، قطع شبکه | چیدمان ۳۲۰/۳۹۰ پیکسل، مجوز و چرخهٔ برنامه |
| ارتقا و بازیابی | نصب تازه، ارتقای روی نسخهٔ قبلی، حذف و بازگردانی | ارتقای نصب موجود، خروج و نصب مجدد |
| صوت | میکروفون و انتقال واقعی به کارمند در صورت استفاده | مجوز میکروفون، پس‌زمینه/پیش‌زمینه و تغییر شبکه |

برای هر دستگاه، نسخهٔ دقیق سیستم‌عامل، هش فایل نصب‌شده، نتیجه و مسئول آزمون را ثبت کنید. نسخهٔ بی‌امضا یا debug برای بررسی فنی مفید است، اما توزیع تأییدشدهٔ ناشر نیست.

## رفع اشکال بسته‌بندی

اگر `prepare:web` خطا داد، وجود و تازگی `frontend/dist/` را بررسی کنید. اگر آزمون نسخه شکست خورد، تمام فایل‌های دارای نسخه و یادداشت انتشار را هماهنگ تغییر دهید. اگر کامپایل اندروید شکست خورد، پیش از تغییر کد برنامه، تنظیم SDK/Java/Gradle wrapper را ببینید. اگر ساخت امضاشده شکست خورد، بدون چاپ رازها در CI، وجود اعتبارنامه و هویت گواهی مورد انتظار را بررسی کنید.

برای رفتار مرورگر [راهنمای رابط](../frontend/README.fa.md) و برای مالکیت محیط و بازیابی [استقرار](deployment.fa.md) را بخوانید.
