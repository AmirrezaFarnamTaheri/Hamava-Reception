# راهنمای استقرار و بازیابی

[English](deployment.md) · [مستندات](README.fa.md)

این راهنما برای مسئول نصب هم‌آوا روی سرور مرکز و حفظ امکان بازیابی آن نوشته شده است. ساختار اصلی یک ورودی HTTPS، سرویس FastAPI، پایگاه PostgreSQL و کارگر مستقل پس‌زمینه است. تلفن و گفتار سرویس‌های جداگانه و اختیاری‌اند؛ برای پذیرش متنی به آن‌ها نیاز نیست.

## ۱. آماده‌سازی میزبان و تعیین مسئول

دامنهٔ متعلق به خودتان، DNS و HTTPS، میزبان Docker با فضای ذخیرهٔ کافی، PostgreSQL **16**، محل امن پشتیبان بیرون از سرور و مسئول فنی/پاسخ‌گو فراهم کنید. مشخص کنید چه کسی اطلاعات مرکز را تأیید می‌کند، مسیر تماس را تغییر می‌دهد، اختلاف پرداخت را پیگیری می‌کند و کلیدها را بازیابی می‌کند. تا وقتی مسیر ارجاع انسانیِ پاسخ‌گو برای خطای خودکارسازی ندارید، تماس بیمار واقعی را نپذیرید.

فایل `compose.yaml` سرویس‌های زیر را تعریف می‌کند:

| سرویس | وظیفه | وضعیت پیش‌فرض |
| --- | --- | --- |
| `db` | پایگاه PostgreSQL | فعال |
| `migrate` | بررسی/ایجاد/ارتقای طرح‌واره پیش از شروع API | پیش از API اجرا می‌شود |
| `api` | برنامهٔ HTTP با FastAPI | فعال |
| `jobs` | صف پایدار و کارگر عملیات | فعال |
| `edge` | درگاه عمومی HTTPS با Caddy | پروفایل `https` |
| `speech` | درگاه گفتار با مدل‌های تأمین‌شده توسط بهره‌بردار | پروفایل `speech` |
| `audiosocket` | سرور خصوصی صوت PBX | پروفایل `pbx` |
| `livekit-worker` | کارگر سمت برنامه برای LiveKit | پروفایل `webrtc` |

پروفایل `webrtc` **سرور LiveKit را نصب نمی‌کند** و پروفایل `pbx` نیز به‌خودی‌خود خط مخابراتی فراهم نمی‌کند. شنوندهٔ AudioSocket روی شبکهٔ خصوصی و بدون رمزگذاری انتقال کار می‌کند و نباید مستقیم در اینترنت عمومی باز شود.

## ۲. ساخت و بازبینی تنظیمات

به‌جای ویرایش `.env` نمایشی، از الگوی تولید استفاده کنید:

~~~sh
python scripts/generate_env.py --host reception.your-domain.example
~~~

ابزار فایل `.env.production` را با مجوز محدود می‌سازد و فایل موجود را بازنویسی نمی‌کند. برای JWT، رمزگذاری، هش جست‌وجو، پایگاه داده، رسانه، پایش و PBX رازهای جدا تولید می‌شود. نسخه‌های بازیابی آن‌ها را در محل امن ثبت کنید؛ پشتیبان پایگاه بدون کلید رمزگذاری برنامه ممکن است قابل استفاده نباشد.

پیش از شروع، حداقل این تنظیمات را بررسی کنید:

| تنظیم | تصمیم موردنیاز |
| --- | --- |
| `ENVIRONMENT=production`، `DEMO_MODE=false` | حالت واقعی بدون حساب و عملیات نمایشی |
| `PUBLIC_HOST`، `PUBLIC_BASE_URL`، `CORS_ORIGINS` | میزبان دقیق HTTPS و مبدأهای مجاز |
| `DATABASE_URL`، `POSTGRES_PASSWORD` | حساب و پایگاه درست و اختصاصی |
| `ENCRYPTION_KEY`، `LOOKUP_HASH_KEY`، `ENCRYPTION_PREVIOUS_KEYS` | برنامهٔ پشتیبان/چرخش و بازیابی مستقل کلیدها |
| `RUN_WORKER=false` | جلوگیری از کارگر تکراری در فرایند API |
| `SPEECH_PROCESSOR_APPROVED`، `SMS_PROVIDER_APPROVED`، `PAYMENT_PROVIDER_APPROVED`، `LIVEKIT_APPROVED` | تا زمان آزمون و بازبینی مستقل هر اتصال خاموش بمانند |
| `MEDIA_DID_TENANTS_JSON`، `HUMAN_TRANSFER_TARGETS`، `AUDIOSOCKET_ALLOWED_CIDRS` | مسیر مرکز/شماره، مقصد انسانی مجاز و شبکهٔ خصوصی |
| `TOOL_TIMEOUT_MS`، `MAX_MEDIA_CONNECTIONS` | مهلت و محدودیت ظرفیت متناسب با میزبان |

اعتبارسنج تنظیمات، فعال‌سازی سرویس با دادهٔ ناقص یا ناسازگار را رد می‌کند. پرچم «تأییدشده» تصمیم بهره‌بردار است و جای بررسی واقعی حساب و قرارداد تأمین‌کننده را نمی‌گیرد.

## ۳. اجرای سرویس اصلی

بعد از تأیید دامنه، کلیدها و برنامهٔ پشتیبان، از ریشهٔ مخزن:

~~~sh
docker compose --env-file .env.production build
docker compose --env-file .env.production --profile https up -d
docker compose --env-file .env.production exec api python scripts/admin.py --email owner@your-domain.example --clinic-name 'نام مرکز' --slug your-clinic
~~~

فرمان ساخت مالک تعاملی است؛ گذرواژهٔ منحصربه‌فرد تعیین کنید و از حساب نمایشی استفاده نکنید. سرویس `migrate` باید پیش از شروع `api` با موفقیت تمام شود. مرکز تازه تا تنظیم خدمات، ساعت‌ها، اطلاعات مصوب، سیاست‌ها و پوشش کارکنان در وضعیت محدود می‌ماند.

هر دو مسیر را بررسی کنید: `/health` دسترسی پایگاه و `/ready` وضعیت وابستگی‌های تنظیم‌شده را گزارش می‌دهد. سالم‌بودن HTTP به معنی آماده‌بودن حساب پرداخت، مسیر صوت یا تأیید مرکز نیست. در محیط عملیاتی با دسترسی مجاز وضعیت هر وابستگی و آخرین مشاهدهٔ آن را ببینید.

## ۴. اتصال‌ها را یکی‌یکی فعال کنید

**تقویم.** تعیین کنید مرجع نوشتن، تقویم داخلی است یا سرویس بیرونیِ پشتیبانی‌شده. قابلیت، شناسهٔ بیرونی، خواندن مجدد و مدیریت نسخه را تنظیم کنید. پیش از تغییر مرجع مرکز واقعی، ثبت تکراری، پاسخ دیررس و نتیجهٔ نامعلوم را آزمایش کنید.

**پیامک و پرداخت.** اعتبارنامهٔ مصوب سرویس و حساب پذیرندهٔ مخصوص مرکز را وارد کنید. مالکیت پیام ورودی و خروجی، رسید، ساعات سکوت، بازپرداخت، بیعانهٔ منقضی و callback نامعلوم را بسنجید. موفقیت محیط آزمایشی دلیل ثبت تسویهٔ واقعی نیست.

**گفتار.** وابستگی‌های اختیاری و وزن‌های تأییدشدهٔ Faster-Whisper/Piper را جدا نصب کنید. نشانی و توکن درگاه، میزبان‌های مجاز، نسخهٔ مدل، محل پردازش و پرچم‌های صریح را تنظیم کنید. پروفایل `speech` را پس از آزمون قالب خروجی، مهلت و مسیر جایگزین فعال کنید.

**تلفن.** خط واقعی اپراتور/PBX و dialplan بررسی‌شدهٔ Asterisk، مسیر خصوصی AudioSocket و مقصد انسانی مجاز لازم‌اند. برای انتقال موفق، غربال‌گری کارکنان، DTMF، رد/پایان مهلت و اتصال شنیداری دوطرفه را روی خط واقعی بیازمایید. RTC مرورگر با LiveKit به سرور و تنظیم شبکهٔ جداگانه نیاز دارد؛ کانتینر کارگر کافی نیست.

در افت سرویس اختیاری، گفت‌وگوی متنی و مسیر تماس کارکنان را حفظ کنید.

## ۵. پشتیبان، مهاجرت و کلیدها

پیش از استقرار جدید یا تغییر طرح‌واره:

1. زمان نگهداری را اعلام و نویسنده‌های API، کارگرها و صوت را متوقف کنید.
2. از PostgreSQL نسخهٔ رمزگذاری‌شده بگیرید و تنظیمات و مدارک نگهداری کلید را جدا پشتیبان‌گیری کنید. `scripts/backup.py` از گیرندهٔ GnuPG مصوب استفاده می‌کند؛ `scripts/config_backup.py` کلید پشتیبان مستقل و فهرست مالکیت کلیدها می‌خواهد.
3. **پشتیبان را روی مقصد خالی و جداگانه بازگردانید** و طرح‌واره، شمارش سوابق، دسترسی به دادهٔ رمزگذاری‌شده و کلید درست برنامه را بررسی کنید.
4. `python scripts/migrate.py` را روی پایگاه موردنظر اجرا و سپس `schema_version`، نمونهٔ نوبت‌ها، سوابق مالی، عضویت مرکز و نسخهٔ سیاست را بررسی کنید.
5. کارگرها و API را از سر بگیرید و پیش از بازکردن پذیرش، سلامت، فرایندهای اصلی، صف و اتصال کارکنان را بررسی کنید.

مسیر فعلی طرح‌واره `0001 → 0002` است و نسخهٔ ناشناخته یا نیمه‌کاره خودکار اصلاح نمی‌شود. مهاجرت معکوس عمومی نداریم. اگر ارتقا شکست خورد، پایگاه **و کلید و تنظیمات متناظر آن** را از پشتیبان آزموده‌شده بازگردانید؛ دستور SQL معکوس حدسی ننویسید. `scripts/rotate_encryption.py` ابتدا پیش‌نمایش و سپس اجرای صریح در حالت آفلاین دارد؛ کلیدهای پیشین تا بررسی همهٔ سوابق و پشتیبان‌های لازم حفظ شوند.

برای زمان‌بندی پشتیبان از `scripts/backup_daily.py` و قالب‌های `deploy/` پس از بررسی استفاده کنید و بازگردانی را دوره‌ای تمرین کنید. وجود یک فایل پشتیبان به معنی امکان بازیابی مرکز نیست.

## ۶. پایش موارد مهم

عمر و حجم صف، عملیات نامعلوم تقویم، سلامت مشاهده‌شدهٔ تأمین‌کننده، تداخل نوبت، خطای تحویل پیام، بدهی پرداخت، شکست اتصال صوت/انتقال، سلامت دیسک و پایگاه و فاصله از آخرین پشتیبان را پایش کنید. نمونه‌های Prometheus و هشدار در `deploy/` قرار دارند و دسترسی به عیب‌یابی باید محدود باشد. گاهی شکایت بیمار اولین نشانهٔ آن است که درخواست «پذیرفته‌شده» هرگز به نتیجه نرسیده؛ شناسهٔ درخواست را نگه دارید و نتیجهٔ مرجع را بررسی کنید.

برای وظایف شیفت، ارجاع خطا و پذیرش راه‌اندازی [عملیات](operations.fa.md) و برای مرزهای سرویس و خطاها [معماری](architecture.fa.md) را ببینید.
