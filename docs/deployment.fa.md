# استقرار و بازیابی

[English](deployment.md) | [مستندات](README.fa.md)

## پیش‌نیازها

استقرار واقعی به دامنهٔ HTTPS متعلق به بهره‌بردار، **PostgreSQL 16**، تنظیمات مصوب مرکز و پردازشگر، مسیر ارجاع انسانی با مسئول پاسخ‌گو، بررسی مستقل حریم خصوصی/بالینی و رازهای قابل‌بازیابی نیاز دارد. حالت نمایشی باید خاموش باشد. ترافیک واقعی را با حساب نمونه، تقویم ساختگی، فایل اجرایی آزمایشی بی‌امضا یا اعتبارنامهٔ بازبینی‌نشده راه نیندازید.

فایل `.env.production.example` تنظیمات را بدون راز قابل‌استفاده نشان می‌دهد. مقادیر مستقل و محرمانه بسازید:

~~~sh
python scripts/generate_env.py --host reception.your-domain.example
docker compose --env-file .env.production build
docker compose --env-file .env.production --profile https up -d
docker compose --env-file .env.production exec api python scripts/admin.py --email owner@your-domain.example --clinic-name 'نام مرکز' --slug your-clinic
~~~

دامنه باید در اختیار خودتان باشد. `.env.production` را محافظت کنید و کلید رمزگذاری، کلید هش جست‌وجو و مواد بازیابی را در مخزن امن بهره‌بردار نگه دارید. `scripts/generate_env.py` فایل موجود را بازنویسی نمی‌کند. سرویس مهاجرت Compose پیش از ترافیک عادی طرح‌وارهٔ **0002** را اجرا/اعتبارسنجی می‌کند. تنظیمات مالک جدید پیش از بازگشایی پذیرش باید منتشر و بازبینی شوند.

## اتصال‌های اختیاری

گفتار جداگانه نصب می‌شود و وزن‌های Faster-Whisper/Piper باید بررسی‌شده باشند. AudioSocket/Asterisk مسیر انتخاب‌شدهٔ تلفن عمومی است و LiveKit برای RTC مرورگر به کار می‌رود؛ هیچ‌کدام به معنی اتصال واقعی اپراتور یا SIP trunk نیستند. قالب‌های استقرار در `deploy/` و پروفایل‌های اختیاری Compose شامل `speech`، `pbx` و `webrtc` هستند. پیش از فعال‌سازی پیامک، پرداخت، تقویم، رسانه یا تماس خروجی، توکن‌های مستقل، دامنه/میزبان مصوب، مسیر انتقال، سیاست قیمت، رضایت، نگهداری داده و شواهد سلامت واقعی لازم‌اند. انتقال غربال‌شدهٔ Asterisk به پذیرش واقعی کارمند و اتصال دوطرفهٔ تأییدشده نیاز دارد، نه صرفاً رویداد یا شروع شماره‌گیری.

## نگهداری و بازیابی

پیش از مهاجرت یا ارتقا، نویسنده‌های API و کارگران پس‌زمینه/صوت را متوقف کنید، از پایگاه و تنظیمات نسخهٔ پشتیبان رمزگذاری‌شده تهیه و رمزگشایی و بازگردانی را در محیط جداگانه بررسی کنید، سپس `python scripts/migrate.py` را روی پایگاه موردنظر اجرا کنید. قبل از ادامه، نسخه و اطلاعات عملیاتی را بررسی کنید. مسیر عمومیِ برگشت مهاجرت وجود ندارد؛ به‌جای SQL معکوسِ موردی، نسخهٔ پشتیبان آزموده‌شده را بازگردانید.

ابزارهای `scripts/backup.py`، `scripts/backup_daily.py`، `scripts/config_backup.py` و قالب زمان‌بندی systemd را فقط پس از بازبینی مسیر، مجوز فایل، رمزگذاری و مقصد به کار ببرید. نسخهٔ پشتیبان بیرون از میزبان استقرار ذخیره و بازیابی به‌صورت دوره‌ای تمرین شود. چرخش کلید رمزگذاری و حفظ کلید قبلی باید با نیاز رکوردهای موجود به رمزگشایی هماهنگ باشد.

## پایش و آغاز سرویس

`/health` سلامت ابتدایی سرویس/پایگاه و `/ready` وابستگی‌های مشاهده‌شده را نشان می‌دهد. قالب هشدارها در `deploy/prometheus-alerts.yml` است. معیارها خصوصی بمانند و عمر صف، نتیجهٔ نامعلوم تأمین‌کننده، تداخل تقویم، خطای پیام، افت صوت، بدهی مالی و وضعیت پشتیبان پایش شوند. آغاز واقعی نیازمند پذیرش بیرونی مخابرات/PBX، فرایند مصوب مرکز، پرداخت/پیامک/تقویم، حریم خصوصی، دستگاه فیزیکی و امضا در موارد مربوط است؛ [عملیات](operations.fa.md) را ببینید.
