# راهنمای توسعه‌دهنده

[English](development.md) · [مستندات](README.fa.md)

این راهنما برای کسی است که کد را تغییر می‌دهد، PR را بازبینی می‌کند یا دنبال علت یک آزمون ناموفق است. اصل کار ساده است: **نتیجهٔ کسب‌وکار را API و پایگاه داده تعیین می‌کنند؛ رابط و سرویس بیرونی فقط آنچه را واقعاً مشاهده کرده‌اند گزارش می‌دهند**.

## محیط توسعهٔ تکرارپذیر

هم‌آوا از Python **3.12** و فایل قفل وابستگی پایتون، ‏Node.js **24** و فایل‌های قفل مستقل npm برای وب، دسکتاپ و اندروید استفاده می‌کند. برای نمونهٔ معمول در پوستهٔ POSIX:

~~~sh
python3.12 -m venv .venv
. .venv/bin/activate
python -m pip install --upgrade -r requirements-bootstrap.txt
python -m pip install -c requirements.lock.txt '.[test,media]'
npm --prefix frontend ci
npm --prefix frontend run build
cp .env.example .env
set -a; . ./.env; set +a
python -m uvicorn receptionist.main:app --host 127.0.0.1 --port 8000 --no-access-log
~~~

در پنجرهٔ دوم با همان تنظیمات `python -m receptionist.worker` را اجرا کنید. اگر کارگر مستقل دارید، در فرایند API مقدار `RUN_WORKER=false` بماند. برای توسعهٔ رابط نیز `npm --prefix frontend run dev` قابل استفاده است؛ Vite درخواست‌های `/api` را به سرور محلی هدایت می‌کند. در ویندوز از دستورهای متناظر بارگذاری محیط استفاده کنید.

نمونهٔ محلی به‌طور پیش‌فرض با مراکز ساختگی و SQLite کار می‌کند. محیط عملیاتی از PostgreSQL **16** استفاده می‌کند؛ پس آزمون هم‌زمانی به پایگاه PostgreSQL آزمایشی جدا نیاز دارد. آزمایش مخرب، مهاجرت یا آزمون مرورگرِ تغییردهندهٔ داده را روی اطلاعات مشتری اجرا نکنید.

## از کدام کد شروع کنیم؟

| نوع تغییر | فایل‌های اصلی | آزمون‌هایی که باید در نظر بگیرید |
| --- | --- | --- |
| نوبت، رزرو موقت، ظرفیت | `backend/receptionist/core.py`، `schemas.py` | تداخل منابع، انقضا، تکرارپذیری، نسخهٔ قدیمی |
| گفت‌وگو و تاریخ فارسی | `voice.py`، `locale.py` | تکرار پیام، اصلاح اطلاعات، تاریخ مبهم، ارجاع انسانی |
| سیاست و مرجع تقویم | `core_policy.py`، `calendar_bridge.py` | مجوز انتشار، نتیجهٔ نامعلوم دوردست، خواندن مجدد |
| وظیفه و پیام | `operations*.py`، `messaging_controls.py` | صف پایدار، ساعات سکوت، ارسال تکراری، مالکیت وظیفه |
| بیعانه و هزینه | `payment_policy.py`، `billing.py` | پذیرش شرایط، مبلغ دقیق، رزرو هزینه و تطبیق |
| دسترسی و نگهداری داده | `security.py`، `privacy_controls.py` | عضویت جاری، لغو رضایت، حذف و پوشاندن اطلاعات |
| صوت و تحویل تماس | `media_api.py`، `media/`، `deploy/asterisk/` | قطع ارتباط، اعتبار کارگر، شاهد اتصال انسانی |
| رفتار رابط | `frontend/src/`، `frontend/scripts/` | نتیجهٔ واقعی API، چیدمان RTL، صفحه‌کلید، بازیابی اتصال |
| امنیت برنامهٔ بومی | `apps/desktop/`، `apps/mobile/` | مخزن نشست، HTTPS، خروج و هویت برنامه |
| بسته‌بندی | `.github/workflows/`، `scripts/collect-release.mjs` | برچسب نسخه، امضا، هش و نام فایل |

رابط کاربری نباید پیاده‌سازی دومِ نوبت‌دهی، پرداخت یا نقش‌ها باشد. اگر فرایندی دشوار است، شکل نمایش آن را بهتر کنید، نه اینکه قواعد سرور را دور بزنید.

## پیش از تغییر رفتار، آزمون بنویسید

برای خطا ابتدا آزمونی بنویسید که مشکل را بازتولید کند. آزمون باید نزدیک قرارداد مربوط باشد. سپس کد را اصلاح، آزمون هدفمند و بعد مجموعهٔ بزرگ‌تر را اجرا کنید. در تغییر نوبت، نتیجهٔ صحیحِ درخواست هم‌زمان و تلاش دوباره را اثبات کنید، نه فقط مسیر موفق معمولی را. برای رسانه، قطع اتصال و رویداد دیررس را بسنجید. در اتصال بیرونی، پذیرش، رد، مهلت‌گذشتگی و نتیجهٔ نامعلوم را جدا آزمایش کنید.

دستورهای عادی:

~~~sh
python -m ruff check backend scripts services
python -m pytest -q
python scripts/protocol_conformance.py --output artifacts/backend/protocol-conformance.json
npm --prefix frontend run build
npm --prefix frontend run test:browser-launch
npm --prefix apps/desktop test
node scripts/check-versions.mjs
node --test scripts/check-docs.test.mjs
node scripts/check-docs.mjs
~~~

برای آزمون مرورگر **ابتدا رابط را بسازید** و سپس ابزار اجرای جداگانه را فراخوانی کنید:

~~~sh
python scripts/ci_ui.py test:ui test:workflows test:conversation test:privacy-notice --port 8137
~~~

`ci_ui.py` برای هر آزمون نام‌برده سرور ساختگی موقت راه می‌اندازد. آزمون‌های دیگری برای اتصال‌ها، رابط انتشار، اطلاع‌رسانی، فهرست انتظار و بیعانه، چرخهٔ RTC، همراه، اتصال و برچسب تأخیر وجود دارد. CI مجموعهٔ گسترده‌تر در `.github/workflows/verify.yml` را اجرا می‌کند.

برای آزمون قفل و هم‌زمانی PostgreSQL ابتدا `TEST_DATABASE_URL` را به پایگاه **مخصوص آزمون** وصل کنید:

~~~sh
python scripts/postgres_stress.py --acknowledge-isolated-test-database --contenders 40 --output artifacts/backend/postgres.json
python scripts/production_smoke.py --acknowledge-isolated-test-database --output artifacts/backend/production.json
~~~

این آزمون‌ها درستی منطق نرم‌افزار را می‌سنجند، نه ظرفیت تماس تلفنی یا بار عملیاتی.

## تغییر طرح‌واره: مسیر ارتقا را نگه دارید

فایل `backend/receptionist/migrations.py` مسیر فعلی **0001 → 0002** را تعریف می‌کند. نسخهٔ `0001` به نصب‌های موجود تعلق دارد و باید همچنان قابل ارتقا باشد؛ حذف آن به این دلیل که نصب تازه مستقیم به `0002` می‌رسد، کاربران قبلی را گرفتار می‌کند.

برای نسخهٔ تازه، مهاجرت رو‌به‌جلو و آزمون ایجاد جدید، ارتقا از تمام نسخه‌های پشتیبانی‌شده، شکست نیمه‌کاره، نسخهٔ ناشناخته، حفظ داده و اجرای دوباره بنویسید. در پایگاه واقعی: نویسنده‌ها را متوقف، پشتیبان آزموده‌شده بگیرید، `python scripts/migrate.py` را اجرا، سوابق را بررسی و کار را از سر بگیرید. طرح‌وارهٔ خراب را پنهانی ثبت یا جداول واقعی را برای عبور از یک آزمون تغییر ندهید. `scripts/migrate_privacy_notes.py` ابزار مستقلِ بهره‌بردار است و جای مهاجرت را نمی‌گیرد.

## چه فایل‌هایی وارد commit نشوند؟

خروجی آزمون در `artifacts/` یا فایل‌های همان اجرای CI بماند. نسخهٔ پایگاه، ضبط صوت، اعتبارنامه، وزن مدل، کلید خصوصی، بستهٔ امضاشده، تصویر مرورگر و فایل JUnit را وارد Git نکنید. آرشیو فقط-کدمنبع با `scripts/make_source_release.py` ساخته می‌شود و فهرست هش آن داخل ZIP است. تولید دوبارهٔ گزارش قدیمی در درخت کد آن را به شاهد فعلی تبدیل نمی‌کند.

PR خوب می‌گوید **چه رفتاری عوض شده، چرا، چگونه آزموده شده و چه چیزی هنوز به خارج از نرم‌افزار وابسته است**. به‌جای ادعای کلیِ «کاملاً آماده»، دستور دقیق، اجزای تغییرکرده و اجرای مربوط CI را نشان دهید.

## به‌روز نگه‌داشتن راهنما

هر راهنمای Markdown نگهداری‌شده نسخهٔ انگلیسی و `.fa.md` دارد. هر دو را در یک PR تغییر دهید. توضیح را ترجمه کنید، اما نام endpoint، مسیر فایل، کلید تنظیمات و دستور اجرایی را دست‌نخورده نگه دارید. جفت‌بودن و صحت پیوندها با `node scripts/check-docs.mjs` بررسی می‌شود. نسخهٔ یادداشت انتشار با `node scripts/check-versions.mjs` کنترل می‌شود.

برای مرز مسئولیت‌ها [معماری](architecture.fa.md)، برای درخواست‌ها [API](api.fa.md)، برای راه‌اندازی [استقرار](deployment.fa.md) و برای روش کار واقعی [عملیات](operations.fa.md) را ببینید.

## پاکسازی امن کدهای بدون استفاده

از ریشهٔ مخزن گزارش را اجرا کنید:

~~~sh
python scripts/audit_dead_code.py --check --output artifacts/dead-code/report.json
~~~

این بررسی واردکردن ماژول‌های پایتون از FastAPI، کارگرها، ابزارها و آزمون‌ها را دنبال می‌کند؛ مسیرهای واردکردن JavaScript/TypeScript و صفحه‌های بارگذاری‌شدهٔ تدریجی را از ورودی وب و برنامه‌های بومی می‌سنجد؛ و ارجاع کلاس‌های Java را از manifest اندروید و ثبت افزونهٔ Capacitor بررسی می‌کند. تابع‌های سطح بالای پایتون و خروجی‌های بدون استفادهٔ رابط نیز گزارش می‌شوند. Ruff واردکردن و متغیر بلااستفادهٔ پایتون را می‌یابد و تنظیمات `noUnusedLocals` و `noUnusedParameters` در TypeScript اعلان‌های زائد معمول رابط را آشکار می‌کنند. CI بررسی وابستگی کد را در کار مستقلی سریع اجرا می‌کند و در کارهای دیگر رفتار سرور، مرورگر، دسکتاپ و کانتینر را می‌سنجد.

هر نامی که بلااستفاده به نظر می‌آید الزاماً قابل‌حذف نیست؛ چارچوب‌ها ممکن است آن را غیرمستقیم بارگذاری کنند. پیش از حذف، دکوراتورهای FastAPI، ثبت مدل SQLAlchemy، مهاجرت‌ها، مسیر preload در Electron، کلاس‌های manifest اندروید، داده‌های آزمون مرورگر و دستورهای package/Actions را بررسی کنید. ابزار بازیابی که بهره‌بردار آن را دستی اجرا می‌کند، حتی اگر فایل دیگری آن را import نکند، همچنان ورودی پشتیبانی‌شده است.

در بررسی سراسری یک ابزار تصویربرداری قدیمی و دو تابع بدون استفاده شناسایی و حذف شدند. ثبت‌های ضروری، نسخه‌های مهاجرت پایگاه، پل‌های بومی و داده‌های آزمون RTC حفظ شده‌اند. گزارش ماشین‌خوان در `artifacts/` ساخته می‌شود و وارد Git نمی‌شود. در پاکسازی بعدی نیز فقط موردی را حذف کنید که ارجاع‌هایش بررسی شده باشد و آزمون مرتبط را اجرا کنید.
